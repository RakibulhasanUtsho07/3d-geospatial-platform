# P2.4 — Cold/warm render and browser-memory benchmark

## Goal

Measure render readiness for the same Dhaka 3D Tiles fixture under two reproducible phases:

- **Cold:** first navigation in the fresh Playwright page/context created for the test.
- **Warm-resource-cache:** reload the same page/context so browser HTTP cache entries may be reused while the Cesium scene is recreated.

This benchmark runs after the P2.3 fixed-camera alignment review succeeds. It intentionally records measurements instead of imposing an arbitrary latency threshold until a stable baseline exists.

## Run locally

Start the app with the fixture generated and served (the normal development pre-hooks perform this):

```bash
npm install
npm run dev
```

In another terminal:

```bash
npm run test:dhaka-3d-tiles-performance
```

The Playwright test uses Chromium/SwiftShader at 1600×950 and writes `artifacts/p2.4-dhaka-render-performance/dhaka-render-performance.json`. Override the output directory with `P2_4_EVIDENCE_DIR`.

## Recorded metrics

- Elapsed milliseconds from navigation/reload start until the page reports ready, visible tile content is confirmed, and two extra animation frames pass.
- Chromium JS heap used/total/limit snapshots, where exposed by `performance.memory`.
- Resource count, transfer bytes, encoded bytes, and count of entries that appear served from cache.
- Canvas drawing-buffer/CSS dimensions, Cesium version, tile load/visible/failure counters.
- SHA-256 of the source feature dataset, tileset and GLB, checked for equality between cold and warm runs.
- SHA-256 checksum for the final JSON report.

## Interpretation and limitations

- This is a repeatable comparative CI measurement, not a benchmark of a physical GPU.
- `performance.memory` covers JavaScript heap only; portable browser APIs do not expose reliable GPU/driver memory, so this does not claim total process or GPU memory.
- A page reload reconstructs the Cesium scene. “Warm” means the HTTP resource cache may be reused, not that an in-memory Cesium scene or tile cache is preserved.
- The benchmark fails on load/readiness errors, failed tile requests, invalid viewport size, or mismatched input hashes. It does not fail merely because a run is slower; establish a runner-specific baseline before setting regression thresholds.
- The P2.3 fixture is a synthetic rectangular prism. Performance results do not establish real building facade accuracy or photogrammetric fidelity.

## First verified CI baseline (2026-10-24)

Source evidence: GitHub Actions run [40070326130](https://github.com/RakibulhasanUtsho07/3d-geospatial-platform/actions/runs/40070326130), artifact `p2-4-dhaka-render-performance`. Artifact checksum validation passed for `dhaka-render-performance.json`.

| Metric | Cold | Warm-resource-cache |
| --- | ---: | ---: |
| Ready time | 4,382.965 ms | 3,737.282 ms |
| JS heap used snapshot | 31.2 MB | 31.2 MB |
| Resource transfer bytes | 1,931,369 | 6,081 |
| Encoded resource bytes | 1,928,069 | 135,995 |
| Tiles loaded / visible events | 1 / 8 | 1 / 8 |
| Failed tiles | 0 | 0 |

The warm phase completed 645.683 ms (14.73%) faster in this single pair. Resource transfer was 1,925,288 bytes (99.69%) lower. Input SHA-256 values matched across phases. The run used Chromium 156.0.8078.4, Cesium 1.146.0, a 1600×950 page viewport, and SwiftShader.

**Do not treat this single pair as a regression threshold.** JS heap snapshots are rounded/coarsely sampled and stayed identical here. The resource transfer difference is consistent with resource-cache reuse, but repeat runs are needed to establish variance and a robust median/P95 baseline.
