# P2.5 — Repeated cold/warm benchmark and baseline aggregation

## Why this follows P2.4

The first verified P2.4 CI pair measured 4,382.965 ms cold and 3,737.282 ms warm. A single pair is not enough to set a performance regression threshold, because GitHub-hosted runner load, browser startup, network/cache state and rendering variability can affect timings.

P2.5 runs five independent paired samples and reports raw measurements plus median and P95 summaries.

## Run locally

Start the generated fixture/app as for P2.4, then run:

```bash
npm run test:dhaka-3d-tiles-performance-repeatability
```

The test writes:
- `artifacts/p2.5-dhaka-performance-repeatability/dhaka-render-performance-repeatability.json`
- `artifacts/p2.5-dhaka-performance-repeatability/SHA256SUMS.txt`

Override the destination with `P2_5_EVIDENCE_DIR`.

## Sampling design

For each of five iterations, create a fresh isolated Playwright browser context, load the review page once (cold), then reload the same page/context (warm resource cache). The Cesium scene is recreated after reload; the warm phase is not an in-memory scene reuse test. Every phase must load visible tile content, have zero tile failures, use a valid canvas viewport, and report identical source/tileset/GLB hashes. Hashes must also remain stable across all ten measurements.

Metrics aggregated with minimum, median, interpolated P95 and maximum:
- Render-ready elapsed time (cold and warm separately).
- Resource transfer bytes.
- JS heap used, where available.
- Paired warm/cold time ratio and warm resource-transfer reduction.

P95 uses linear interpolation over the sorted sample values. The report always includes raw per-iteration results so summaries remain auditable.

## CI artifact

CI uploads `p2-5-dhaka-performance-repeatability` and keeps it for 14 days. The summary is comparative evidence from headless Chromium/SwiftShader, not a physical-GPU benchmark.

## Threshold policy

No arbitrary latency pass/fail budget is set yet. First collect repeatability data on a stable, like-for-like runner and compare multiple commits. A later guard should use an explicit baseline and a tolerance informed by observed variance; do not derive a regression threshold from the P2.4 single-pair sample alone.

Portable `performance.memory` gives a coarse JS heap estimate only. GPU/driver memory is not claimed. The 3D Tiles asset remains a synthetic rectangular-prism placement fixture, so this is performance/caching validation rather than a model realism test.
